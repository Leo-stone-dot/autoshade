# 测试与架构验收原则

状态：当前生效

相关文档：`docs/BEHAVIOR_PROTECTION.md`、`scripts/mutation_gate.py`、`scripts/agent_quality_gate.sh`、`docs/TEST_GAP_CHECKLIST.md`

## 一句话原则

**测试验收行为，架构验收代码结构；红灯必须对应产品行为坏了。**

这里的“架构验收”包括编译器、类型、可见性、clippy、独立脚本 gate 和 CI 门禁。不是所有规则都必须写成 clippy。

## 两类验收

### 行为测试

行为测试验收用户或调用方能观察到的结果：

- 状态变化
- 返回值
- 文件结果
- 错误类型和错误文案
- 用户可见的 UI
- 资源上限
- 性能预算
- 并发、幂等和部分失败

### 架构验收

架构验收代码允许怎么写：

- 层依赖
- 允许和禁止导入
- 禁用类型或 API
- 单门入口
- 调用次数和顺序
- 文件布局
- 函数存在性
- 目录和模块边界

如果一条架构规则不能用编译器、类型、可见性或 lint 稳定表达，优先改设计，使违规写法无法通过编译；不要把它写成源码扫描测试。

## 测试编写原则

1. **只测行为，不测实现路径。**
   断言状态、返回值、文件、错误、UI 或资源结果，不断言私有字段、helper 名字、调用顺序和文件布局。

2. **一个 case 一个主张。**
   测试名直接说“什么条件下，系统应该做什么”。不要用 `test_foo`、`works` 这类名字。

3. **红灯必须对应产品故障。**
   如果一次等价重构让测试变红，而产品行为没变，这个测试在锁实现，必须改掉。

4. **断言公开契约，不绑定当前实现。**
   视图测试只断言用户看到的结果，不绑定 egui/GPUI 的具体类型和 API；换 UI 框架时，行为测试不应重写。

5. **每个新不变量配一个能杀死它的 mutation。**
   改坏对应行为，测试必须变红。只写一个永远为真的断言没有价值。

6. **测试独立、确定、可并行。**
   临时目录按进程和用例隔离；环境变量、cwd、时钟、网络、系统字体必须显式控制或 gate；不依赖测试顺序。

7. **真实路径优先，mock 只替代外部系统。**
   不 mock 被测对象本身；mock 不能决定断言结果。外部付费、模型、网络调用可以 stub 或 gate，但要在测试名或注释里说明。

8. **正常路径、边界、错误路径同等重要。**
   空输入、上限、下限、非法值、超时、并发竞争、部分失败都应有对应 case。

9. **默认快，慢测试显式 gate；速度不参与入选。**
   付费、真实 RAW、模型、长时间性能测试必须默认跳过，并给出启用方式和原因。这里的 gate 只决定运行时机，不决定是否纳入测试范围；核心行为不能因为测试慢而消失。反过来，一个测试快也不是保留它的理由；没有行为语义的快速 case 同样删除。

10. **测试数据合成或脱敏。**
    不放私人照片、密钥、机器绝对路径；fixture 要能稳定构建，构建失败不能静默变成空测试。

11. **平台相关逻辑先提取成纯函数。**
    平台分支在对应平台验证；不能执行的另一平台分支，不要靠源码文本证明存在。

12. **测试描述目标行为，不描述重构中间态。**
    测试应该能在合理重构后继续通过；如果它只对当前文件拆分方式成立，就不是行为测试。

## 测试选择口径

测试范围不是按“核心/外围”做一次永久筛选。风险只决定先补哪一批，不决定一个行为是否进入范围。

1. **所有可观察行为都在范围内。** 包括顶层用户工作流，也包括公开的领域计算、解析、格式化、几何和像素原语；只要调用方能观察到结果，它就是行为，不是“实现细节”。
2. **私有实现不单独立项。** 私有 helper 的行为必须通过公开入口产生可观察结果；不为 helper 名字、调用顺序或文件布局写测试。
3. **按风险排序，不设名额。** P0/P1 先补；P2、低频边界和外围体验随后补。低风险不代表永久不测，也不存在“核心 case 占掉外围 case 名额”的预算。
4. **每个行为同时考虑正常、边界、错误、超时、并发和部分失败。** 不能只写一个 happy path 就宣称该行为已覆盖。
5. **纯计算逻辑用合成输入测试。** 外部系统用边界 stub 或显式 gate；慢或付费只改变运行时机，不改变是否纳入范围。
6. **覆盖率只用于发现未触达代码。** 它不是目标、分母、优先级或完成条件；也不得用提高百分比替代补行为。覆盖率不得作为个人、团队或 Agent 的考核、排名、OKR、奖金、CI 门槛、PR 准入或“测试质量已达标”的结论；一次统计只能触发盲区审计，不能直接转成补行数任务。
7. **快慢不是入选或删除标准。** 快慢只决定放在哪个 gate；先证明行为和失败后果，再决定运行时机。

未覆盖记录只说明该次测量未观察到执行，不自动证明缺少行为测试：还需核对运行 gate、平台、子进程统计和实际断言。发现漏保必须从具体行为及故障后果出发，不能按未覆盖行号批量造 case。

一条行为如果没有测试，不能因为“当前覆盖率看起来还可以”而视为已覆盖；一条测试如果没有对应的产品故障语义，也不能因为“覆盖率上升”而保留。

## 测试构造模板

新增一个 case 前，先写清楚下面五件事；写不出来，说明还不应该写测试：

1. **行为契约**：`在什么前提下，系统应该做什么`，测试名直接使用这句话。
2. **公开入口**：通过用户操作、公开 API、文件结果或可见 UI 进入；不直接测私有 helper。
3. **真实前提**：fixture 必须能稳定构造，失败不能静默变成空测试；外部系统只允许 stub 或 gate。
4. **可观察断言**：断言返回值、状态、文件、错误、UI、资源上限或部分失败结果；一个 case 只主张一件事。
5. **能杀死它的 mutation**：说明改坏哪个产品行为会让这个 case 变红；不能说明就先不把 case 标记为完成。

构造时优先使用共享的测试沙箱和合成数据，而不是在每个 case 里复制临时目录、环境变量和清理逻辑。共享设施只能负责隔离、构造和清理，不能决定被测对象的断言结果。

## 测试构建方法

测试按**行为域**组织，不按生产源文件拆分的中间态组织：

- 纯计算、解析和领域规则放在独立的集成测试中，用合成输入验证输出。
- 需要进程级环境变量的 Store/fit 测试使用 `tests/support/mod.rs::ScopedEnv`：进程内互斥、`Drop` 恢复，并由测试政策 gate 阻止裸环境写入。
- 外部网络、模型、真实 RAW、长性能路径默认不阻塞快速套件，但必须保留显式 gate、启用方式和失败语义。
- GUI 测试断言用户可见状态或动作结果，不把 egui/GPUI 类型、源码文本或 helper 调用顺序写进断言。
- 临时目录按进程和 case 隔离；共享 helper 只消除重复，不隐藏失败、不吞掉错误。

每次改动先问“哪个产品行为可能坏”，再写能让它变红的 case。覆盖率报告可以在行为审计之后用于找漏掉的代码区域，但不能反过来决定测试范围或评价测试人员的产出。

## 禁止事项

1. 禁止在测试里读 Rust 源码。
   包括 `include_str!` 指向 `.rs`、遍历 `src`、`gui_source()`、`contains("fn ...")`、数调用点、查注释或源码标记。

2. 禁止把架构约束写成测试。
   层依赖、允许导入、单门规则、调用次数、文件布局和类型禁用应交给编译器、类型、可见性或 lint。

3. 禁止“函数存在/被调用”式断言。
   这类测试不验证行为，只验证当前代码形状。

4. 禁止锁定内部实现。
   私有字段、helper 名字、临时文件布局、精确调用顺序，除非它们本身就是公开契约。

5. 禁止 vacuous test。
   没有 premise、只 `assert!(true)`、catch-all 后什么都不检查，都属于无效测试。

6. 禁止依赖测试顺序和全局状态。
   不依赖前一个测试留下的文件、环境变量、单例、缓存或工作目录。

7. 禁止无界 sleep。
   并发等待用 channel、condvar、timeout；不要用 sleep 猜时序。

8. 禁止长期 ignore flaky 测试。
   要么修，要么有明确名字和原因的 gate；不能让它长期红着或被静默跳过。

9. 禁止为测试在生产代码里加隐藏开关。
   测试专用分支会变成第二套行为；需要 seam 时，设计成真实契约。

10. 禁止用测试锁死重构中间态。
    测试不应要求某个函数必须放在某个文件、某个调用必须出现几次。

11. 禁止在未证明 lint 覆盖前删除 case。
    部分覆盖不算覆盖；一个 case 里只要还有 lint 覆盖不到的断言，就不能删。

## 归属边界

| 应该由测试验收 | 应该由编译器、类型、lint 或 gate 验收 |
| --- | --- |
| 状态变化、返回值、文件结果 | 层依赖、允许导入 |
| 错误类型与用户可见文案 | 禁用类型、禁用 API |
| UI 可见结果、布局约束 | 单门规则、调用次数 |
| 资源上限、性能预算 | 文件布局、函数存在性 |
| 并发、幂等、部分失败 | 目录/模块边界 |

## 一条规则的归类方法

遇到一条新规则，按顺序判断：

1. 用户能观察到违反后的结果吗？
   能：写行为测试。

2. 违规写法能否被编译器、类型、可见性或 lint 机械判定？
   能：写类型、可见性或 lint 规则。

3. 两者都不能稳定表达吗？
   改设计，让违规写法无法通过编译；否则只保留代码评审，不进入自动化验收。

不要用以下方式证明架构约束：

- 在测试里搜索源码字符串
- 数某个函数出现次数
- 要求某个 helper 必须存在
- 要求某个调用必须写在某个函数里
- 要求每个调用点写注释

## Agent 编码质量门禁

自动门禁通过 Rust 社区的 `cargo-mutants` 检查：**对本次选中的、可编译的故障反例，实际运行的测试能否发现它？** 它不自动生成完整的行为集合，也不能证明未生成的故障或未执行的场景已获保护；不以自建函数登记表代替这项检查。

`scripts/mutation_gate.py` 是一个薄 wrapper，不维护函数全集、不解析 rustdoc、不保存测试名：

- `--worktree`：收集当前工作区 diff，交给 `cargo-mutants` 只跑改动行重叠的 mutation。
- `--in-diff FILE`：PR/CI 模式，只跑与 diff 重叠的 mutation。
- `--files FILE...`：显式指定整个文件。
- `--full`：完整仓库 mutation，慢，必须显式启用；可用 `--shard k/n` 分片。
- `--list`：只列出将被测试的 mutation，不执行。
- `--re REGEX`：只跑列出名称匹配该正则的 mutant，用于定向证明一个新增不变量。
- `--test-arg ARG`：重复传给 cargo test；慢用例需要 `--test-arg=-- --test-arg=--ignored`，再传测试名。

`scripts/agent_quality_gate.sh` 是 agent 结束一次编码前应运行的单一入口：

```bash
scripts/agent_quality_gate.sh
```

它依次运行：

1. `cargo test --locked --release --features gui`
2. `cargo clippy --locked --release --all-targets --features gui -- -D warnings`
3. `python3 scripts/check_test_policy.py`（含 `--self-test`）
4. `python3 scripts/check_architecture.py`（含 `--self-test`）
5. 文本资源、文档漂移和发布声明 gate
6. `python3 scripts/mutation_gate.py --worktree --jobs 2`

确定、自包含且无需外部服务的本地进程/回环 HTTP 测试进入默认套件，
使普通测试与默认 mutation 执行同一保护。慢速或有外部依赖的用例使用显式 gate；
只在 mutation 前运行一次慢套件，不等于它在每个 mutant 下执行了。

PR/CI 的增量门禁是：

```bash
git diff --unified=0 origin/main...HEAD > /tmp/autoshade-change.diff
python3 scripts/mutation_gate.py --in-diff /tmp/autoshade-change.diff --jobs 2 --in-place
```

完整 mutation 需要显式运行；下面是可用命令，不代表仓库已经配置夜间或发布调度：

```bash
python3 scripts/mutation_gate.py --full --shard 1/8 --jobs 2
```

工具版本固定为 `cargo-mutants 27.1.0`：

```bash
cargo install cargo-mutants --version 27.1.0 --locked
```

### 失败语义

- 改动触及生产 Rust，但 `cargo-mutants` 一个 mutant 都没生成：失败，不允许静默跳过。
- 有 `MissedMutant`：门禁失败，需核对该变化是否确实破坏了约定行为。只有非等价的行为破坏未被发现，才构成漏保证据；不能把等价 mutation 当产品故障。
- `Timeout`、baseline 失败、cargo-mutants 内部错误：失败。
- `CaughtMutant` 也需要核对失败原因：若只是无关测试偶发失败、启动失败或资源错误，不算有效保护；应排除干扰后重跑，确认对应行为断言失败。
- diff 只改文档：跳过 mutation；常规文档 gate 和代码评审仍然有效。
- diff 只改测试：必须用 `AUTOSHADE_MUTATION_FILES=src/...` 指明被保护的生产文件；没有指定就失败，不能静默跳过。指定后对整个生产文件跑 mutation，慢用例用 `--test-arg` 让对应 case 真正执行。
- 改动行没有 mutant：失败，不退回到整个生产文件。测试同时变更时，可通过
  `AUTOSHADE_MUTATION_FILES` 显式指定被保护的生产行为；纯生产改动则必须另给可执行的
  定向故障反例。运行同文件的无关 mutant 不能证明当前改动。

私有函数不需要单独的测试清单。它们的行为通过公开入口验证；如果改动触及私有实现，`--worktree`/`--in-diff` 仍然会跑对应的 mutation，避免把行为藏到 helper 后面绕过门禁。

`cargo-mutants` 生成不了候选时，不能补测试名蒙混，也不能为了通过门禁缩小生产 API。应提供可执行、能让测试变红的定向反例，并明确记录工具未覆盖的范围；当前 wrapper 不会自动消费这份人工证据，其失败状态必须如实报告。

## 行为严重度

严重度按“违反后的影响”认定，不按代码位置、模块大小或测试数量认定。无法判断时向上归类。

### P0

违反后可能造成不可接受后果：

- 数据丢失、损坏、覆盖或不可恢复
- 安全、隐私或授权边界失效
- 崩溃、panic、挂起、OOM 或无界资源消耗
- 并发或幂等性错误导致状态损坏、重复写入或丢失写入
- 核心工作流完全不可用，且没有安全恢复路径

### P1

违反后核心产品行为错误，但影响有边界：

- 主要用户工作流失败或产生用户可见的错误结果
- 导入、导出、保存、恢复等核心结果错误，但没有直接造成数据丢失
- 资源预算、超时或并发约束被突破，但系统仍能安全返回
- 必需的错误没有出现，或错误进入错误的通道
- 部分失败没有披露，用户无法知道实际结果
- 核心 UI 控件存在但实际不改变结果

### P2

违反后只影响外围体验或安全回退路径：

- 文案、布局、视觉细节或非核心交互问题
- 罕见边界情况，但有明确且安全的回退
- 非核心诊断信息不完整
- 不属于 P0/P1 的性能或可维护性问题

**P0/P1 合称关键行为。** 它们是设计评审和测试优先级的标签，不进入自动门禁的分母。自动门禁检查选中 mutation 的 outcome；P0/P1 的价值是决定先补哪些测试、先处理哪些存活 mutant，不代表该工具已穷尽关键行为。

不建立以行覆盖率、CBC 或其他比例为核心的考核指标。需要跟踪时，只维护“关键行为 → 证据 case → 能杀死它的 mutation”清单，不用比例做个人/团队排名，也不把某个比例作为准入条件。行覆盖率只用于发现未触达代码，同样不能替代 mutation。

## 完成定义

一个行为 case 只有满足以下全部条件才算完成：

1. 测试名描述条件和目标行为。
2. 测试断言公开结果，不锁实现。
3. 测试有明确运行 gate；默认快速或显式慢 gate 都算完成，运行时间不决定是否完成。
4. 测试有真实 premise，不是 vacuous test。
5. 对应 mutation 能让测试变红。
6. 运行 `scripts/agent_quality_gate.sh` 并报告实际结果和选择范围；若其增量范围没有选中该行为，须另行定向验证，不能用无关绿灯替代。未通过的门禁保持未通过，不以文字说明冒充成功。

架构约束只有在以下条件之一成立时才算完成：

1. 编译器或类型系统拒绝违规写法。
2. 可见性限制拒绝违规写法。
3. clippy 或独立 gate 能稳定、机械地判定违规。

否则该约束不进入自动化验收，必须先改设计或降级为代码评审事项。
